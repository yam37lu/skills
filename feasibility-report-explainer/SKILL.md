# 可研报告通俗讲解

把一份写给专家评审看的可行性研究报告，讲成业务同事和非本专业读者能听懂的技术说明：项目为什么做、要解决什么问题、研究了什么、用了哪些技术、每项技术具体干什么、各课题分别做什么、课题之间怎么衔接。

默认"详细讲解"，但每一节都先给结论再展开。读者默认是非本专业但关心项目的人（业务负责人、产品经理、新入职同事、评审旁听者）；如果用户表明自己是同行专家，减少类比、增加机制与指标口径的解释。

## 边界：只讲学术内容

- **要讲**：研究背景与需求、国内外现状、科学/技术问题、研究内容、技术路线与方法、关键技术、数据与实验、考核指标、预期成果、课题划分与衔接。
- **不讲**：人员配置、经费预算、进度安排、组织管理、单位资质、知识产权归属等管理性安排是否合理、是否有纰漏。用户不问就不提；用户问也只陈述报告内容，不展开评审式评价。若用户明确要求评审这些安排，说明本 skill 只负责学术内容讲解，管理评审需另行处理。
- **例外**：当管理性内容本身承载技术事实（如试点场景、数据来源、算力/设备条件、协作分工涉及的技术边界），只提取其中的技术事实，不评价安排好坏。
- **不补写**：报告没有的技术细节不要替它补全。可以补充领域常识，但必须标明是"背景补充"；报告自己没说清的，明确写"报告未展开"。

## 工作流程

### 1. 拿到全文，而不是只读目录

- 用户只给标题、或说"这个报告"时：先在工作目录找同名或最近修改的 `.docx` / `.pdf`，确认后再读；找不到就问路径，不要猜内容。同时给了多份材料时，以可行性研究报告主体为准，商业计划书、评审表、预算附件只提取技术信息。
- 确认文件路径与格式。`.docx` 用工作区自带的 python-docx 提取；`.txt` / `.md` 直接读取；PDF 先尝试文本提取，扫描版 PDF 读不出文字时要说明并请用户提供 docx 或可复制文本。
- 提取脚本：`scripts/extract_report.py`。它会保留标题层级、表格和图片位置，输出一份便于按章节阅读的 Markdown，并打印统计信息和目录。先调用 `load_workspace_dependencies` 取得 Python 路径再运行，不要安装依赖。
- 长报告分段读：先看目录和一级标题，再逐章读正文。不要因为篇幅长就只读摘要或"研究内容"一节——背景和现状往往决定了对技术路线的理解。
- 顺手记录几个元信息：报告标题、项目类型（技术研究/产品研发）、实施方式（自主实施/联合攻关/揭榜挂帅）、研究周期、课题或研究方向的数量。

### 2. 建立"报告地图"（内部笔记，不必全部输出）

先按常见章节定位（不同单位模板略有差异）：

| 报告章节 | 讲解时要提取什么 |
|---|---|
| 目的和意义 / 项目必要性 | 背景、业务场景、痛点、必要性论证 |
| 国内外研究水平综述 | 现有水平、与目标的差距、创新点落在哪 |
| 理论和实践依据 | 原理、技术基础、关键难点 |
| 研究内容和实施方案 | 核心：做什么、分几块、怎么做、谁依赖谁 |
| 预期目标和成果形式 | 指标、交付物、验收口径 |
| 承担单位条件 / 进度 / 经费 / 审查意见 | 与学术讲解无关，跳过；只把设备、数据、试验条件当作技术前提 |

再按章节抽取：

- **背景链**：行业/政策趋势 → 业务场景 → 现有做法 → 具体痛点 → 不解决会怎样。
- **问题清单**：报告点名了哪几个技术瓶颈，每个瓶颈对应哪项研究内容。注意"问题"和"研究内容"要能一一对上，对不上就是讲解的重点。
- **课题清单**：报告怎么划分课题/研究方向/子任务（"课题一/二/三"、"研究内容 1/2/3"、"方向一/二/三"都算）。每个课题记：目标、研究内容、技术路线、输入输出、考核指标、成果形式。
- **技术清单**：出现的每个技术名词、英文缩写、算法、框架、数据标准。记它在哪个课题、解决什么问题、报告给了什么指标。
- **成果清单**：原型系统、算法引擎、技术报告、专利、软著、论文、标准，分别由哪个课题产出。
- **数据流**：各课题之间谁给谁提供什么（影像→模型→要素→服务→系统），这是讲清"课题关系"的关键。

### 3. 判断课题结构，不要硬造

- 报告明确分课题：按课题逐一讲，保留报告原来的编号和名称。
- 报告只分"研究内容/研究方向"：视为课题来讲，但开头说明"报告称其为研究内容 X"。
- 报告是一个整体、没有子课题：按"研究内容模块"拆分，不虚构课题层级。
- 课题超过 5 个：先给一张总表（课题/目标/关键技术/产出），再逐题展开；可以问用户想先深入哪一个。
- 课题之间有重叠或边界不清：在"课题关系"里点明，这属于学术内容，应当指出。

### 4. 写讲解

完整结构见 `references/output-template.md`，动笔前读一次。核心是回答六个问题：

1. 这个项目一句话是干什么的？
2. 为什么现在要做？（背景与痛点，带报告里的真实场景）
3. 总体上研究什么？（目标、几条主线、最终产出）
4. 每个课题具体研究什么？（问题→内容→技术路线→关键技术→指标→与其他课题的关系）
5. 用到的技术分别是干什么的？（跨课题技术总表 + 2-4 个关键技术的展开）
6. 做完之后能带来什么变化？（能力、指标、成果，不写市场收入承诺）

写作要求：

- **先结论后解释**：每节开头 1-2 句"人话总结"，再展开细节。段落控制在 5 行以内。
- **术语首次出现**：中文名（英文全称，缩写）→ 一句话定义 → 在本项目里负责什么。之后统一用缩写。
- **技术必须回答"没有它会怎样"**：用报告里的痛点或失败现象作对照，而不是孤立地介绍技术。
- **类比要用，但要收边界**：类比后补一句"这个类比只说明……，实际还涉及……"。
- **指标要具体**：引用报告的分辨率、精度、召回率、效率、覆盖范围等数字，并用参照物解释它大概是什么水平（能做什么、不能做什么），不夸大。
- **区分事实层级**：报告原文 / 领域常识补充 / 你的推断，三者不混写。推断用"可以理解为""通常做法是"，并说明报告是否支持。
- **不堆形容词**：不写"赋能、闭环、抓手"式空话；每个技术点落到"输入什么、怎么处理、输出什么"。
- **不替报告圆场**：报告前后矛盾、指标口径不清、技术路线缺环（学术层面）时，指出并说明对结论的影响。

### 5. 自检后再交付

- 每个课题是否都回答了：解决什么问题、研究什么、用什么技术、技术干什么、产出什么？
- 每个技术名词是否都有通俗解释，且解释了"在本项目中的作用"？
- 是否出现了报告没有的数字、结论、论文、标准？（有则删除或标注为推断）
- 是否混入了人员、经费、进度、组织管理的评价？（有则删除）
- 非本专业读者只看"一页纸总结"，能否说出项目在做什么、各课题分别干什么？

## 输出与篇幅

- 默认输出完整讲解，约 2000-4000 字，按报告体量调整；用户要"简短/3 分钟版"时给 500-800 字加一张技术总表。
- 长报告分节输出：先给总览和讲解目录，再按课题分节，不要一次性倾倒超长文本。
- 默认用中文回答；用户换语言提问时跟随用户语言，技术名保留英文缩写。
- 默认直接在对话里输出 Markdown。用户要求落盘或要 Word/PDF 时再调用 `office` 相关技能，不要默认生成文件。
- 讲解中尽量标注来源章节（如"报告第四章研究内容 2"），方便用户回查。
